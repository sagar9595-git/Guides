Epic and Story Writing Guide

Portfolio level

What makes a good Epic

A container for a large, uncertain solution — too big for one team or one iteration. It exists to test a hypothesis, not to guarantee a feature list.

End-to-End Flow

Big enough to improve a full business flow across multiple teams, not just one team's to-do list.

Single Owner

One named leader is accountable for the result and can clearly explain why this epic matters.

Evidence-Backed Case

Decision is based on facts, expected outcomes, and business impact, not opinions alone.

Testable Idea

Frame it as an idea to validate with measurable outcomes, not a fixed list of features.

Smallest First Release

Define the smallest version that can prove value early before committing full funding.

For customer group who need this improvement,
epic name is a type of solution
that helps them get this benefit.
Compared with how work is done today,
this solution is better because.
✕ Weak epic

"Access rights to MS Dynamics should be managed centrally. In our org, application access is managed in oneIDM, which holds personnel data for new user registration. In oneIDM, requests are received to grant and revoke access for onboarding/offboarding. Roles can be requested for additional licenses or extra data/function access. IDM roles should clearly show what they grant and be simple to request." Useful context, but still broad, solution-heavy, and not measurable.

✓ Strong epic

"For application requesters, line managers, and IT access admins who need controlled MS Dynamics access, Centralized Dynamics Access Management in oneIDM is a role-based access process for baseline onboarding/offboarding and approved add-on roles that makes requests clearer, faster, and auditable. Compared with today's mixed role definitions and manual clarifications, it targets 95% role-request clarity, 30% faster approval cycle time, and 100% traceable grant/revoke history in the first PI."

tap the card to flip

What the strong example fixed
  • Named the real actors: requesters, managers, and IT access admins.
  • Clarified scope: baseline onboarding/offboarding plus approved add-on roles.
  • Shifted from solution dump to value: clearer requests, faster approvals, auditable access.
  • Added measurable outcomes: clarity, cycle time, and audit traceability targets.

Epic Template

Fill the Must-have cards first to define a usable epic, then complete Optional cards as details mature.

Must-have first Needed before splitting cleanly into stories

1. Description

"As an [role], I want [capability], so that [benefit]" — one sentence naming the need, not the solution.

2. Problem Statement / Status Quo

Today's pain and why it matters now — grounds the epic before anyone starts designing.

4. User Impact

Names the real personas affected and how their day-to-day work changes — not a generic "users."

6. Business Value

Why it matters to the business — tied to a measurable outcome or strategic driver.

8. Out of Scope

Explicitly lists what this epic will not cover, with links to the epics that do.

9. Dependencies

Names the upstream systems, teams, or master data this epic relies on.

10. Proposed Story Split

A rough first cut of stories — a planning placeholder, deleted once real stories are created.

Optional later Add when implementation details and supporting artifacts are ready

3. Process Visualization

Link to the current or target process diagram so readers see where this epic fits end-to-end.

5. Requirements

Bullets on what the solution must support, each independently checkable. What, not how.

7. Notes / Open Questions

Stakeholder Q&A captured as it's resolved — keeps decisions traceable instead of re-litigated later.

11. Solution Design

Links to the capability doc, solution design, and CoP approval — pointers, not duplicated content.

12. How Might It Be Implemented

The high-level technical approach agreed with architecture — enough to estimate, not a full design.

13. Effort (Design / Build / Test)

Rough sizing per work type — feeds prioritization.

Anti-patterns

Epic Watch-outs

The most common ways an Epic quietly goes wrong.

Epic smells

  • Untestable hypothesis — epic states expected benefits, but no failure condition or stop criteria.
  • Local optimization metrics — success is measured only by internal output (features shipped), not business or user outcomes.
  • Hidden dependency mesh — data, security, and process dependencies appear late because they were captured as assumptions.
  • Overloaded MVP — "MVP" still contains multiple capabilities that cannot be validated independently.
  • Component-based decomposition — stories split by system layers (UI/API/data) instead of end-to-end user value slices.
Team level

What makes a good Story

A story is one small result a team can finish in one iteration and verify with clear acceptance criteria.

As a specific user role,
I want to do one concrete action,
so that I get one clear benefit.
1

Write

Write one role, one action, and one benefit. Keep it short.

2

Discuss

Confirm scope with PO and team so it fits one iteration.

3

Verify

Add acceptance criteria everyone can test and agree on.

Given a line manager submits a oneIDM request for a new MS Dynamics user
When they select the baseline onboarding role
Then role description is clear and the request is routed for approval with audit trace
✕ Weak story

"As an access requester, I want oneIDM role management for MS Dynamics so onboarding and offboarding are easier." Good direction, but still too broad and not testable.

✓ Strong story

"As a line manager, I want to request the MS Dynamics baseline onboarding role in oneIDM, so that new team members get the right default access on time." Acceptance criteria: role description is visible before submit, request can be completed in 3 minutes or less, and approval/audit trail is recorded.

tap the card to flip

What the strong story fixed
  • Narrowed scope: one role request flow, not full access management.
  • Named a real persona: line manager, not a generic requester.
  • Made value explicit: correct baseline access on time for new joiners.
  • Added testable criteria: clarity, cycle time, and audit trail checks.
Quick test

Run every story through INVEST

Six letters, six questions. Tap one open to see the red flag that means it's failing.

IIndependent›
Little to no dependency on other stories — it can be reordered or reprioritized freely.
Red flag: "Part 2 of 3 — can't start until story #114 merges."
NNegotiable›
Captures intent, not a fixed contract — the how gets settled in conversation with the team.
Red flag: Reads like a spec with every field pre-decided, no room to discuss approach.
VValuable›
Delivers value a customer or the business can actually perceive.
Red flag: "Refactor the OrderService class" — no user-facing outcome named.
EEstimable›
The team knows enough about it to size it — no giant unknowns hiding inside.
Red flag: "We don't know what 'faster' means — can't estimate this."
SSmall›
Fits comfortably inside one iteration — days, not weeks.
Red flag: Same story "in progress" for three sprints running.
TTestable›
Has clear acceptance criteria the team can verify objectively.
Red flag: "Improve the user experience" — done according to whose judgment?
When a story fails "Small"

How to split it

Split along a real seam in the work — never just "part 1 / part 2."

Workflow steps

Search → filter → sort, one story per step.

Business rules

Standard pricing this story, promo pricing the next.

Data variations

CSV import now, API import later.

Interface variations

Web this sprint, mobile the next.

CRUD operations

Create and Read now; Update and Delete as follow-ups.

Major vs. minor effort

Ship the common 80% path, defer the rare edge case.

Test scenarios

Happy path first, negative/edge cases as a separate story.

Anti-patterns

Story Watch-outs

The most common ways a Story quietly goes wrong.

Story smells

  • Looks right, still too big — story format looks correct, but still bundles workflow, policy, and data changes in one item.
  • Vague acceptance criteria — words like "intuitive" or "seamless" with no observable pass/fail check.
  • Integration checked too late — story is marked done in isolation while dependency contracts remain unverified.
  • Missing run-support checks — logging, monitoring, access controls, or rollback expectations are omitted from done criteria.
  • Works only with sample data — story passes with happy-path sample data but fails against real production-like scenarios.
  • Hidden dependency — external team/system input is phrased as "expected" rather than planned and tracked.
